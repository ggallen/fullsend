## Plain-language terms

- A **skip** is a valid decision not to start, or to stop, a stage because its conditions are not met. It should finish successfully with a reason. It should not look like a software failure.
- An **eligibility rejection** is the rule saying “this work should not run.” For example, a human-authored PR without `fullsend-fix` may be ineligible for the fix agent.
- A **failed eligibility check** is a rejected item reported using an error result. The rule may have made the right decision, but a non-zero exit can turn that ordinary skip into a red workflow.
- A **fix issue** is still only a request or report in the issue tracker. A change is implemented only when the relevant PR is merged and the current path actually uses it.

## What is a report, and what is a fix?

| Record | What it tells us | What it does not prove |
|---|---|---|
| Spreadsheet issue | A person saw a behavior, wants a policy, or proposes a change. The role code groups related requests. | That the proposed change was implemented or that every similarly coded issue is a duplicate. |
| Linked PR in a customer/repository | The PR where an unnecessary run, duplicate review, or other example occurred. | That the PR changes Fullsend. |
| Fullsend or agents PR | A proposed or landed change to the platform/agent. Its merge state and files show what it changes. | That the change covers every event path or every issue with the same rule slug. |

## Cross-cutting findings

### Eligibility and routing

The same policy is not necessarily expressible at one point. Event filters can reject obvious cases before a runner starts; a harness CEL trigger can decide whether the selected agent matches a normalized event; a pre-script can use fresher forge or tracker state before sandbox creation; and execution-time checks may still be needed when the input can change. These layers must agree on the decision and its result.

On the analyzed Fullsend snapshot, the reported non-coder-bot mismatch still exists: the `pull_request_review` route sends any bot-authored PR with a bot `CHANGES_REQUESTED` review to `fix` ([workflow route](../.github/workflows/reusable-dispatch.yml#L465-L485)), while the execution eligibility script rejects unknown bots without `fullsend-fix` and exits 1 ([script](../.github/scripts/check-fix-eligibility.sh#L67-L88)). That is the exact pattern in #6791 and #7092: the route launches work that the later check predictably rejects, then the expected rejection can appear as failure. The human-authored path from completed issue #5811 is present in the current workflow.

### Retro and platform branches

The GitLab harness router still returns `retro` for each authorized closed/merged change proposal without checking whether a meaningful agent stage ran ([router](../internal/dispatch/router.go#L197-L213)). That confirms why the zero-agent and platform-branch reports overlap. It does not make them identical: “no agent stage,” “automated dependency update,” and “Fullsend-managed branch” are different reasons, and the same branch may need filtering in a GitHub shim before a run reaches a harness router.

The current per-repo GitHub shim subscribes to every label/unlabel event and excludes only `fullsend/scaffold-install` ([template](../internal/scaffold/fullsend-repo/templates/shim-per-repo.yaml#L26-L46)). Therefore the broad branch-prefix request (#7015 family) and actionable-label filtering (#1362/#6244/#7281 family) are separate checks in the same generated workflow. The open PR #6994 has not changed the checked-in template.

### Skip and outcome

Fullsend already has an accepted pre-script output protocol: `skipped=true` or exit 78 requests a neutral skip, the CLI reports a skipped status and exits successfully before sandbox creation ([ADR 0072](../docs/ADRs/0072-pre-script-output-protocol.md), [protocol](../docs/normative/prescript-output/v1/README.md)). Agents PR #1783 adopted that signal for closed/merged review PRs and skipped authors. That resolves the review-stage pre-script examples #2809/#3690. It does not by itself fix every workflow-level problem: a route can avoid dispatch earlier, the caller must stop later steps, and only one layer should post a skip notification. Genuine API, authorization, or script failures must still fail.

### Concurrency and repeated work

Accepted [ADR 0106](../docs/ADRs/0106-serialize-agent-runs-and-coalesce-subsequent-events.md) already defines automatic-run coordination: preserve the active run and coalesce later matching events into at most one pending run for the same harness and canonical entity. That is a stronger and clearer shared contract than ad hoc per-agent locks. It does **not** mean “run once ever on a PR”: completed-work receipts (#2401), unchanged diff/SHA checks (R9/R10), and event coalescing (R15) answer different questions.

The older merged PR #2465 introduced `cancel-in-progress: true`, and the analyzed `main` still uses it for each stage (for example [the fix group](../.github/workflows/reusable-dispatch.yml#L2065-L2068)). So GitHub dispatch has **not yet implemented ADR 0106’s preserve-active decision**: a later matching event can still cancel the active run. Merge-queue readiness (#2866) is also separate: a queue must know which review sources are required and wait for their completion.

### Agent-specific and post-processing policies

Review depth and bot fast paths (R2/R23), effort-based auto-promotion (R19), ready-for-merge labels (R14/R24), and status comments (R18/R22) should not be collapsed into one eligibility predicate. They have different owners and consequences. Fullsend owns shared authorization, dispatch, run coordination, skip transport, and workflow status. The agents repository owns agent-specific pre/post behavior, review depth, and agent-authored output. Generated repository shims must stay aligned with the shared routing contract.

## Recommended consolidation and ownership

1. **Treat the bucket IDs above as the deduplication proposal.** Keep one canonical issue per shared behavior, but carry the listed distinct cases into its acceptance criteria. Do not close every item sharing R1, R2, R9, R14, R15, R18, R23, or R24 as one duplicate.
2. **Use #939 for the broad no-agent retro rule, but decide in its acceptance criteria what counts as meaningful prior work.** Keep review-only/no-finding cases as explicit tests; bot authorship and dependency titles are clues, not the policy itself.
3. **Keep #4006 (retro-only dependency policy) separate from #4377/#5067 (multiple-stage bot/dependency policy).** The issue history explicitly says the latter loses scope if merged into the former.
4. **Keep #6791 and #7092 as two linked requirements.** Fix #6791 at routing when author/label state is already available; keep the execution-time eligibility guard for fresh state, and make an expected rejection a successful skip. A real permission/API failure remains a failure.
5. **Use #1356 for unchanged semantic diffs and #8389 for a previously reviewed head SHA.** They are different keys. Keep rapid-event coalescing and zero-file PRs as separate cases. #9275 closes #8619 and part of the wider R9 family only.
6. **Use ADR 0106 as the run-coordination contract.** Check each GitHub, GitLab, reusable-workflow, manual, and automatic path against its key and preserve-active/one-pending rule. Do not claim an issue is fixed merely because a concurrency group exists.
7. **Keep agent behavior and output policy scoped to the agent.** Review depth, bot fast paths, effort-based promotion, outcome labels, and review comments need separate acceptance criteria in the agents repository; Fullsend owns shared routing and status contracts.
8. **Before implementation, reconcile tracker labels on the ambiguous closures:** #7281/#7359 point at one another despite comments naming #7281 as canonical; #7493’s retro symptom was closed to the R11 branch-filter issue #7015; #8139 was closed to #6791 even though its title describes a human-gate-only case; #7284’s canceled-run comments are not the same output as stale “working” comments. The bucket table keeps these distinctions visible.
